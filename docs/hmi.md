## 1. 目标与非目标

### 1.1 目标

一个按键、一块 160×80 彩屏，做出的东西只有两件事：

1. **屏幕 = 常驻状态栏**。时间、IP、亮度这些"看一眼就想知道"的信息永远在顶部一行，日期、电流、信号在底部一行，不需要任何操作就能看到；
2. **按键 = 直达动作**。切换场景、开关灯、调亮度三个高频功能，分别对应三个手势，按下去立刻有反应，屏幕上立刻看得见变化。

判定标准：

| 优先级 | 能力 | 判定标准 |
|---|---|---|
| P0 | 开关灯 | 按一下就有反应（含双击窗口的开销，见 §3.2） |
| P0 | 调亮度 | 按住可连续调，屏幕上看得见数值和条 |
| P0 | 切换场景 | 不用记编号，屏幕上显示预设名 |
| P0 | **永不丢失恢复通道** | 按键接管后，进 AP / 恢复出厂依然可用 |
| P1 | 状态栏常驻 | 顶行时间 / 日期 / 亮度 / 信号，底行 IP / 电流，无需操作 |
| P2 | 操作反馈 | 每次按键后屏幕上有明确的、1.5 秒的反馈 |

### 1.2 非目标（明确不做）

- **不做菜单**。没有列表、没有光标、没有层级导航。所有按键动作直达。
- **不做多级/模态界面**。屏幕任何时刻只有两种呈现：**闲置态**和**操作态覆盖层**（后者 1.5 秒后自动消失，不是需要用户退出的"界面"）。
- **不做中文字库**（V1）。GLCD 6×8 字体只有 ASCII；详见 [§10](#10-开放问题)。
- **不做参数编辑**（速度、强度、调色板选择等）。它们要么用不上，要么超出了一个按键的表达能力——留给 Web UI。若日后确实需要，走 [§9](#9-后续演进) 的菜单方案。
- **不替代 Web UI**。所有配置项仍以 `cfg.json` + 设置页为准。

## 2. 现状与硬约束

### 2.1 硬件事实

| 项 | 值 | 影响 |
|---|---|---|
| 按键 | GPIO9，`BTN_TYPE_PUSH`(2)，`INPUT_PULLUP`，按下拉低 | 见下方 strapping 警告 |
| 屏幕 | ST7735，160×80 横屏，RGB565 65K 色，SPI 27 MHz，**无背光控制引脚**（`TFT_BL=-1`） | 可用颜色表达状态；但无法息屏、无法调背光 |
| 字符网格 | **26 字符 × 10 行**（6×8 GLCD，text size 1） | 两条状态栏各 11px = 22px = 全屏 27.5% |
| 全屏刷新 | 160×80×2 = 25.6 KB ÷ 27 MHz ≈ **7.6 ms**（含命令开销约 10 ms） | 全屏重绘 ≈ 半个 LED 帧（23 ms） |
| 单行刷新 | 160×8×2 = 2.56 KB ≈ **1 ms** | 逐区域重绘必须成为常态 |

> ⚠️ **GPIO9 是 ESP32-C3 的 BOOT/下载 strapping 引脚**。开机瞬间若被拉低，芯片直接进 ROM 下载模式，**根本进不了固件**。
> 因此：**(a) 绝不能设计"开机时按住按键"触发的功能**；**(b) 用户按着按键上电会表现为"设备不启动"，`readme.md` 的排障章节要写明这一条**。

### 2.2 现有按钮行为（`wled00/button.cpp`）

WLED 对 **button 0** 有一组**写死的**行为，无法通过配置关闭：

| 常量 | 值 | 行为 | 位置 |
|---|---|---|---|
| `WLED_DEBOUNCE_THRESHOLD` | 50 ms | 短于此时长的按压丢弃 | `button.cpp:7` |
| `WLED_LONG_PRESS` | 600 ms | 按住 600 ms → `longPressAction()`（button 0 默认 = 随机色） | `button.cpp:8` |
| `WLED_DOUBLE_PRESS` | 350 ms | 双击窗口 | `button.cpp:9` |
| `WLED_LONG_AP` | 5000 ms | **松手时**判定：按住 >5 s → `initAP(true)` | `button.cpp:11` |
| `WLED_LONG_FACTORY_RESET` | 10000 ms | 按住 >10 s → `WLED_FS.format()` + `doReboot` | `button.cpp:12` |

两个关键机制：

1. **`UsermodManager::handleButton(b)` 是接管钩子**（`button.cpp:278`）：
   ```c
   if (UsermodManager::handleButton(b)) continue; // did usermod handle buttons
   ```
   **任意一个 usermod 返回 true，原生逻辑对该按钮整体跳过**。注意它是"非短路 OR"——所有 usermod 都会被调用，只要有一个返回 true 就跳过。
2. **按钮状态是全局的**：`std::vector<Button> buttons`（`wled.h:646`，`struct Button` 定义在 `wled.h:622`）对外可见，`bool isButtonPressed(uint8_t b)` 在 `fcn_declare.h:31` 声明，usermod 可以直接采样。

### 2.3 一个后果严重的细节

如果 HMI 采用"前 5 秒接管、超过 5 秒放手让原生处理"的做法，**恢复通道会失效**。原因是 `handleButton()` 里更新 `pressedBefore` / `pressedTime` 的代码在 `continue` 之后（`button.cpp:304-305`），被接管期间这些字段不会推进；一旦某轮开始返回 false，原生看到的是一次"全新的按下"，`pressedTime` 从零开始，松手时长永远到不了 5 s。

> **结论（本方案的安全底线）：HMI 一旦接管 button 0，就必须自己完整复刻 5 s / 10 s 两个逃生阈值，而不是"让路"给原生。** 见 [§6.4](#64-逃生通道必须复刻)。

### 2.4 现有显示 usermod 的形态

- 单文件 `usermods/ST7735_display/ST7735_display.cpp`，`TFT_eSPI tft` 是**全局非静态对象**（同文件内）。
- `loop()` 里有 **1 秒轮询门槛**（`USER_LOOP_REFRESH_RATE_MS`，`:93`）+ `needRedraw` 变更检测。**按键操作需要一条绕开这 1 秒的立即重绘路径**。
- `handleButton` **未实现**，按钮完全走原生逻辑。
- `USERMOD_ID_ST7735_DISPLAY = 59`（`const.h:255`，登记在 `pin_manager.h:80`）。

## 3. 按键映射（核心决策）

### 3.1 三个手势对三个功能

| 手势 | 动作 | 生效时机 | 屏幕反馈 |
|---|---|---|---|
| **短按** | **开 / 关灯** | 松开后 350 ms（双击窗口过期） | 主区大字 `ON` / `OFF` |
| **双击** | **切换预设**（下一个场景） | 第二次**松手**时（≥50 ms 消抖后） | 主区大字显示预设名 + `n/N` |
| **长按** ≥600 ms | **调亮度**，按住每 150 ms 走一步 | 按住 600 ms 时立即开始 | 主区变成数值 + 全宽进度条 |
| 超长按 5 s | 启动 AP（与原生一致） | 松手时 | — |
| 超长按 ≥10 s | 恢复出厂（与原生一致） | 松手时 | — |

这个映射不是随便定的：它正好是廉价 LED 控制器和 WLED 自己的 `button 1`（`button.cpp:27` 短按切效果）的约定，用户不需要重新学。

**双击切的是预设，不是效果**（这处偏离见 [§3.4](#34-为什么切的是预设而不是效果)）。

### 3.2 那个绕不开的 350 ms

**问题**：短按和双击共用"按一下"这个前导动作，设备必须等 350 ms 才能确认"用户不会再按第二下"。这 350 ms 落在了**开关灯**上——恰恰是最高频、最希望"跟手"的动作。

**备选方案的代价**（都考虑过，都不如上面）：

| 方案 | 做法 | 代价 |
|---|---|---|
| B | 短按=切模式、双击=开关灯 | 没有副作用，但"单击开灯"的肌肉记忆被打破，每次开关多按一下 |
| C | 只保留两个手势（短按=开关、长按=亮度），切模式交给 Web/预设 | 零延迟，但丢掉一个 P0 功能 |
| D | 短按立即开关，双击再"撤销开关并切模式" | 开灯时会肉眼可见地闪一下错误状态，不可接受 |

**决定：采用 §3.1 的方案 A，并把双击窗口做成可配置项**：

- `hmiDoubleMs` 默认 **350**（与 `WLED_DOUBLE_PRESS` 对齐）；嫌迟钝可以降到 250；
- **设为 0 时双击手势被完全关闭**，短按立即生效、零延迟（代价是失去按钮切预设的能力）。

这样"要跟手"和"要功能全"两种偏好都能满足，不用在文档里替用户做取舍。

### 3.3 调亮度的方向

一个键调亮度需要两个方向，翻转的动作沿用 **WLED 原生做法**（`button.cpp:309` 的 `buttonBriDirection`），但**翻转的有效范围收窄到"一次调节"**：

- 一次调节的**第一次长按 → 变亮**；亮度浮层还留在屏幕上时再长按 → **变暗**；浮层掉回主界面之后，下一次长按仍从**变亮**开始。
- 换句话说，方向不是按钮身上的一个状态位，而是**属于当前这个浮层**：浮层在，"翻转"=把刚才那次反过来（要减亮）；浮层没了，"翻转"=变亮。所以**减亮的窗口就是 `hmiOverlayMs`**（默认 1.5 s），和浮层的存活时间同一个数，不引入第二个计时量。
- 这样修的是原 WLED 行为在单键上的一个坑：方向会跨越两次互不相干的调节一直记着，用户"调亮 → 松手 → 再调亮"得到的却是变暗。
- 代价：用户按下去之前不知道这次是加还是减。**因此状态栏/覆盖层必须在 600 ms 内把方向显示出来**——见 [§4.3](#43-操作态覆盖层)。

**步进曲线**（否则要么调不快、要么调不细）：

| 已走步数 | 步进 | 间隔 |
|---|---|---|
| 1–5 | 4 | 200 ms |
| 6+ | 16 | 150 ms |

前 5 步用于精细微调，之后加速。全程（0↔255）约 **2.5 秒**。

### 3.4 为什么切的是预设而不是效果

**问题**：效果表有 200 多项。双击若只前进一个，从一个效果走到另一个常用效果可能要按上百次——单键的输入带宽是固定的（每个动作几百毫秒），**线性浏览 200 项在物理上就是慢的**。

两条出路：减小候选集，或提高单位时间的步进。后者（连击加速、按住扫描）解决不了根本问题——高速扫过时名字根本看不清，而"给当前效果加星"这类操作在单键上又找不到空闲手势。所以走前者。

**决定：双击在预设集内前进**，自动跳过被删掉的 ID 空洞并循环回卷（最后一个 → 第一个）。

| 理由 | 说明 |
|---|---|
| 候选集已经是筛选过的 | 预设是用户在 Web UI 里自己挑出来、命名的，通常十来个，而不是 200 个 |
| 设置界面现成 | WLED 的预设页已经能增删改、命名、排序。**不需要在固件里另造一套收藏集**，也不需要自定义设置页与持久化 |
| 预设是"场景"不是"效果" | 它连带调色板、颜色、亮度一起存。切预设 = 换一个完整观感，这正是日常想要的粒度 |
| 存储现成 | `/presets.json` 由 WLED 自己管，usermod 只读不写 |

**代价与取舍**：

- **应用预设会改亮度**。这是预设的本来语义——只想要效果的话，保存预设时不勾亮度/颜色。
- **仍然只能前进**。预设集小，按两下就绕回来了；单键没有余量再放一个后退手势，这个结论与 V1 时相同。
- **一个预设都没有时退化为"下一个效果"**，手势不留空洞。

**实现上必须绕开的两个坑**（细节见 [§6.6](#66-与-wled-状态的交互)）：

1. **`currentPreset` 不能用作按键游标。** 两个原因。一是 `handlePresets()` 在本 usermod 的 `loop()` **之后**才跑（`wled.cpp:149` 对 `:104`），屏幕会慢一拍。二是它对本按钮应用的每一个预设都读回 0：`handlePresets()` 先赋值（`presets.cpp:201`），隔一行就调 `stateUpdated()`（`:208`），而 `deserializeState()` 刚刚置上的 `stateChanged`（亮度变了 `json.cpp:380`、segment 变了 `:363`）会让 `led.cpp:93` 立刻把它清掉。WLED 只在自己网页用的 `pd` 路径上打了补丁恢复（`json.cpp:527` 原话："stateUpdated() will clear the preset, so we need to restore it after"），而 `applyPreset()` 是排队路径，没有这一步。所以 usermod 自己维护游标，`currentPreset` 只当作"外部应用了预设"的提示。

   > 注意：**单按一次亮度并不会清零它**——那条路径直接写 `bri`，`bri != briOld` 会进入外层分支，但 `stateChanged` 始终没被置起。它不用被亮度清零，因为它本来就是 0。倒是 [§6.6](#66-与-wled-状态的交互) 的写回要用这个游标，因为那时 `currentPreset` 已经没东西可用了。
2. **预设 ID 有空洞**，不能简单 `+1`。而 `getPresetName()` 每次调用都读一次文件，且拿不到 JSON 锁时与"预设不存在"返回**同一个** `false`（`presets.cpp:87`），不能用来探测存在性。存在性改由一个 32 字节的位图回答，位图由一次文件扫描建立、`presetsModifiedTime` 变化时重建。

### 3.5 逃生通道的三重保险

HMI 接管后，恢复路径按可用性排列：

1. **HMI 复刻的 5 s / 10 s 超长按**——日常可用，且是唯一不需要屏幕配合的；
2. **硬件后门：按住 GPIO9 上电 → ROM 下载模式**——永远有效，不依赖任何固件逻辑；
3. （预留）若日后加菜单，菜单里再加"启动 AP / 恢复出厂"显式入口。

外加 WLED 自带的 `handleBootLoop()`（连续崩溃自动降级恢复配置）。

## 4. 屏幕布局

80px 高 = 10 行，切成**顶栏（1 行，y=0..10）** + **主区（y=12..67，56px）** + **底栏（1 行，y=69..79）**，两条 1px 分隔线。

分栏依据是**变化频率和谁能改它**：顶栏放按键能改的和自己会变的（时间/日期/亮度/信号），底栏放两个又慢又宽、偶尔才看一次的值（IP/电流）。

每栏 11px 而不是字体需要的 8px：顶栏的两个图标——信号格和太阳——都是 11×11。**再小就画不出"一个圆核 + 离核有一定间隙的光芒"**，而那正是太阳不像十字的前提（见 §4.1 末）。

### 4.1 状态栏（常驻，一上一下）

```
   0 ┌──────────────────────────────────────────────────────────────┐
     │ 14:32  9/19              ☀ 65%                  ▁▃▅█         │  顶栏
  11 ├──────────────────────────────────────────────────────────────┤
     │                        （主区 56px）                          │
  68 ├──────────────────────────────────────────────────────────────┤
  71 │ 192.168.1.42                                1234 mA          │  底栏
  79 └──────────────────────────────────────────────────────────────┘
```

精确坐标（26 字符 × 6px）：

**顶栏** —— 时间 / 日期 / 亮度 / 信号：

| 元素 | x 起点 | 宽度 | 备注 |
|---|---|---|---|
| `14:32 ` | 0 | 36 px | 6 字符，定宽，AM/PM 时是 `11:05A` |
| `9/19` | 37 | 30 px | 5 字符，最长 `12/31`；**只到月/日，不显示星期** |
| 亮度图标 | 107 | 11×11 px | 矢量太阳，见下 |
| `65%` | 120 | 24 px | 4 字符，**左对齐**：数字与太阳保持 2px，而不是与右边缘对齐 |
| 信号图标 | 149 | 11×11 px | 四格柱状，见下；**右贴边** |

**底栏** —— IP / 电流：

| 元素 | x 起点 | 宽度 | 备注 |
|---|---|---|---|
| IP | 0 | 90 px | 15 字符 = 最长 IPv4，定宽 |
| `1234 mA` | 右对齐 | 54 px | 9 字符，`65535 mA` 是最坏情况；右对齐让 `mA` 不动，数字向左长 |

**信号用四格柱状图标，不显示数字**：2px 宽、间隔 1px、高度 4/6/8/10，自左向右在 `quality` 越过 25/50/75/100 时依次点亮。无链路时四格用**槽色**画而不是不画——图标保持可辨认，只是全灭。用图标就必须接受 25% 的分辨率，这是它的代价。

**亮度用太阳图标而不是进度条**：**核心是半径 2 的实心圆**，且**不再变大**——半径 1 的 `fillCircle` 画出来是个加号；而半径 3 的核会把光线需要的间隙吃掉。所以档位改由**光线的长短**表达：**八根光线始终一起出现**，离核心 1px；`bri ≤ 64` 时每根只有 1px（整个太阳缩在 9×9 内），`> 64` 时加长到 2px，太阳撑满 11×11 的包围盒。

> 早期版本是"核心 → 四根正交光线（>64）→ 再加四根对角光线（>176）"，结果是**中段亮度下屏上只有"一个圆盘 + 四根轴向光线"，也就是一个十字**——对角光线才是让它"放射"起来的那一半，不能排在最后一档。

`bri == 0` 时是一个空心圆环，仍然是亮度图标，只是"不发光"。光线与核心之间的 1px 间隙是它读起来像太阳的关键。

两个图标都用矢量图元画而不是存位图：太阳取**当前灯色**（和覆盖层进度条同一个色源，见 §5），位图做不到。旁边的百分比负责精确值，图标负责一瞥。

> 顶栏中段（x=67..106）留了 40px 空档，是两条栏里唯一有余量的地方。底栏则刚好排满：15 字符的 IP 槽之后只剩 16px。

**降级行为**（必须实现，否则状态栏会显示垃圾）：

| 情况 | 处理 |
|---|---|
| NTP 未启用 / 未同步 | 顶栏时间槽显示 `--:-- `，日期槽留空 |
| AP 模式 | 底栏改为 AP 地址（警示色）+ 右对齐的 AP 密码，**电流让位**——此刻没有任何人需要知道电流，而密码没有别处可看 |
| WiFi 未连接 | 底栏 IP 槽显示 `No link`（警示色），顶栏四格全灭 |
| IP 超过 15 字符 | 不可能（IPv4 最长 15），定宽槽内截断 |

### 4.2 主区 · 闲置态

按键之间的常态。注意：**时间/日期/亮度/信号/IP/电流都已经进了状态栏，主区只剩"这块灯在干什么"**。

```
  12 ├──────────────────────────────────────────────────────────────┤
  26 │                        Blink                                 │  效果名 text size 2（12×16）
  46 │                       Rainbow                                │  调色板名 text size 1
  68 ├──────────────────────────────────────────────────────────────┤
```

- 效果名用 **text size 2**（12×16px），居中对齐——它是主区的主角，也是"切换模式"的反馈落点。
- 效果名和调色板名各自维护脏标志，改名不动调色板，反之亦然。
- **速度、强度、当前预设、帧率都不显示**。四个都是"偶尔才想看一次、而且看了也改不了"的值，却要占掉主区下半屏；挪走以后效果名有整屏的留白，一瞥就知道现在是什么效果。要看它们用 Web UI。若日后证明需要，主区有 56px 的余量可以加回来（对应代码里的 `Y_MAIN+34` 往下）。
- 若要加回预设名，需要读 `/presets.json`，**必须异步取**（JSON 缓冲是全局单例，见 §10-6）；抢不到锁的那几轮先只显示编号。

### 4.3 操作态覆盖层

**这是"不做菜单"之后，唯一需要用户理解的新概念，但它只是反馈、不是界面。** 任何按键动作发生时，主区临时变成该动作的调节视图；**松手后 1.5 秒自动回落到闲置态**，用户不需要退出、不需要确认。

**调亮度**（长按期间）：

```
  12 ├──────────────────────────────────────────────────────────────┤
  18 │  Brightness                              +              65%  │  标题 + 方向 + 数值
  42 │  ██████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  │  全宽进度条（8px 高）
  68 ├──────────────────────────────────────────────────────────────┤
```

- **方向指示（`+` / `−`）必须在按住 600 ms 内出现**——这是 §3.3 那个"用户不知道方向"问题的唯一补偿。
- 进度条颜色 = 当前灯色，色太暗时回退白色（§5）。
- 主区仍然显示全宽进度条，尽管顶栏已经改成图标：调亮度时手指还按着，这一屏是**当前操作的主视图**，8px 高、26 字符宽的条比顶栏那个 11px 的太阳精确得多；太阳是给"平时瞟一眼"用的，两者分工不同。

**切换预设**（双击后）：

```
  18 │  Preset                                           3 / 8      │
  26 │                        Party                                 │  大字预设名
```

标题左右两半都是 13 字符的定宽字段，所以 `Preset` 与 `Effect` 互切不会互相留字。三种形态：

| 情形 | 标题 | 计数 | 大字 |
|---|---|---|---|
| 在预设里，且名字已读到 | `Preset` | `3/8` | 预设名 |
| 在预设里，但预设没名字（或名字还没读到） | `Preset` | `3/8` | 该预设把灯带切到的效果名 |
| 一个预设都没有 | `Effect` | `3/220` | 效果名（即 V1 的行为） |

**开关灯**（短按后）：

```
  18 │  Power                                                       │
  26 │                        OFF                                   │  ON 用绿色，OFF 用灰色
```

**开机自检**（可选，V2）：上电后 2 秒内主区显示版本 + IP，方便现场确认设备起来了。

### 4.4 关灯态

`bri == 0` 时，闲置态主区退化为一个居中大字 **`OFF`**（灰色），两条状态栏**保持常驻**（时间/日期/IP 在关灯时仍然有用，这也是它和"整个屏幕黑掉"的区别）。顶栏的亮度图标此时是空心圆环。

> 因为 `TFT_BL=-1`（无背光控制引脚），**无法做"关灯后屏幕也熄灭"**。这是硬件限制，需求上要接受：屏幕会一直亮着。若这个不可接受，需要换带 BL 控制的模块或飞线——见 [§10](#10-开放问题)。

## 5. 配色规范

彩屏的自由度需要用规则约束，否则很容易做成"花但看不清"。两条原则：**沿用 STATUS 屏已有的取色习惯**（保证观感一致），**颜色只用来区分语义，不用来装饰**。

取色沿用同一套语义：日期 `TFT_SILVER`、时钟/亮度 `TFT_WHITE`、网络类 `TFT_GREEN`（信号按档位变橙/红）、电流 `TFT_ORANGE`、效果名 `TFT_CYAN`、调色板名 `TFT_YELLOW`。HMI 把它们收成一批语义常量：

| 语义常量 | 色值 | 用途 |
|---|---|---|
| `HMI_C_BG` | `TFT_BLACK` | 背景（保持纯黑） |
| `HMI_C_LABEL` | `TFT_SILVER` | 状态栏的标签、次要文字 |
| `HMI_C_VALUE` | `TFT_WHITE` | 时间、IP、数值 |
| `HMI_C_ACCENT` | `TFT_CYAN` | 效果名 |
| `HMI_C_OK` | `TFT_GREEN` | `ON`、信号良好、`+`（变亮） |
| `HMI_C_WARN` | `TFT_ORANGE` | 信号弱、`No link`、复位确认 |
| `HMI_C_DANGER` | `TFT_RED` | 信号差、恢复出厂 |
| `HMI_C_OFF` | `0x7BEF`（中灰） | `OFF` |
| `HMI_C_BAR_BG` | `0x2104`（深灰） | 进度条槽 |

可读性规则（6×8 GLCD 笔画只有 1 px，这几条不是审美问题而是能不能看清）：

1. **纯蓝 `TFT_BLUE`(0x001F) 与深红禁止用于文字**，黑底上几乎不可读；只能用作填充块。
2. **背景保持纯黑**，深灰背景会显著吃掉对比度，小屏没有余量。
3. **进度条槽不要用纯黑**，否则和背景糊在一起、看不出量程；用 `HMI_C_BAR_BG`。
4. **不要用当前效果/调色板的输出色去染文字**——LED 输出每帧都在变，界面会看起来在闪。唯一的例外是**亮度**：顶栏的太阳图标和覆盖层的进度条都取当前灯色（"颜色 = 灯的颜色"正是最有信息量的表达），两者共用同一个 `levelColor()`，并且做兜底——该色太暗时回退 `HMI_C_VALUE`。这也是太阳用矢量图元画、不存位图的原因。
5. **信号格的"灭"用槽色 `HMI_C_BAR_BG` 而不是黑色**——四格全灭时图标仍然成形，"无信号"和"这块区域什么都没有"是两回事。同理太阳在 `bri == 0` 时画空心环而不是留白。
6. 色值一律走上面的语义常量，不要散落字面量；注意 TFT_eSPI 用的是 **RGB565 16 位**色值（`tft.color565(r,g,b)`），与 WLED `colors.h` 的 `RGBW32` 24/32 位色不是一回事，不要混用。
7. 彩屏**不增加带宽成本**：`fillRect` 的像素数与单色排版完全相同（§2.1 的 25.6 KB 已按 16 bpp 计算），彩色进度条是"免费"的。

## 6. 技术实现方案

### 6.1 归属：放进 ST7735_display usermod，不新建 usermod

| 方案 | 评估 |
|---|---|
| **A. 扩展 `ST7735_display`（推荐）** | 屏幕与按键是同一件产品形态；`tft` 实例、引脚、重绘逻辑、变更检测全部现成；`handleButton` 本来就是 `Usermod` 的虚函数 |
| B. 新建 `usermods/hmi_menu/` | 需跨 usermod 拿 `tft` 实例与重绘入口（`tft` 是那个文件里的全局对象，跨翻译单元要 `extern` + 依赖头文件，脆弱），还得自造一层 `getUMData()` 协议。**收益只在"同一套 HMI 要同时服务 ST7789 显示 usermod"时才成立** |

### 6.2 代码结构

```
usermods/ST7735_display/
├── ST7735_display.cpp    现有：显示驱动 + Usermod 外壳（改动见 §6.3）
├── ui_hmi.h              新增：手势状态机 + 视图状态
├── ui_hmi.cpp            新增：实现
├── library.json          不改（目录下所有 .cpp 都会被编译）
└── readme.md             增补"按键与状态栏"章节
```

按三层拆开，**关键是手势层不依赖显示、视图层不依赖硬件**，这样两端都能单独验证：

```cpp
// ui_hmi.h  (不 include TFT_eSPI，不碰 GPIO)

// 1) 手势层：电平 -> 动作
enum class HmiAction { NONE, POWER_TOGGLE, MODE_NEXT, BRI_STEP, ESCAPE_AP, ESCAPE_RESET };

class HmiGesture {
  public:
    // 每个 loop 调用一次，返回本轮产生的动作（一次至多一个）
    HmiAction update(bool pressed, uint32_t now);
    int8_t    briDirection() const { return _dir; }   // +1 / -1，供覆盖层显示方向
  private:
    bool     _pressedBefore = false;
    uint32_t _pressedTime = 0, _waitTime = 0, _repeatAt = 0;
    int8_t   _dir = 1;
    uint8_t  _steps = 0;      // 按住已走步数，用于 §3.3 的加速曲线
    bool     _escaped = false; // 本次按压已判定为逃生，不再产生其他动作
};

// 2) 视图层：只认"发生了什么"，只输出"要画什么"
enum class HmiOverlay { NONE, POWER, MODE, BRIGHTNESS };

class HmiView {
  public:
    void onAction(HmiAction a, const HmiGesture &g, uint32_t now);
    HmiOverlay overlay() const;
    bool overlayExpired(uint32_t now) const;   // 1.5 s 后回落
    // 供绘制函数查询的只读状态
    uint8_t  overlayValue() const;
    uint8_t  overlayTotal() const;
};
```

动作的实际执行（改 `bri`、`effectCurrent`）放在 usermod 里做，**不放进 `HmiGesture` / `HmiView`**——保持这两层是纯逻辑，可以在 PC 上用一段喂时间序列的仿真循环做回归（本仓库没有单元测试框架，这是唯一可行的自动化验证手段）。

### 6.3 与现有显示 usermod 的接线点

| 位置 | 改动 |
|---|---|
| `:375` `loop()` 的 1 秒门槛 | 改为"**有按键活动时立即通过**"（HMI 触发重绘时清零 `lastUpdate` 或引入 `forceRedraw`）。不改这里，按键后屏幕会延迟最多 1 秒才更新，体验很差 |
| `:401` `if (!needRedraw) return;` | 改为 `needRedraw \|\| hmi.hasDirtyRegion()` |
| `drawScreen()` | 拆成 `drawStatusTop()` / `drawStatusBottom()` / `drawMainIdle()` / `drawMainOverlay()`，各自维护一个脏标志；主区内部再按字段比对 |
| `:372-424` 的整体重绘 | 从"全屏 `fillScreen` + 重画"改为**按脏区域重绘**；全屏重绘只在进出覆盖层和切换旋转方向时发生 |
| **新增** `handleButton(uint8_t b)` | `b == 0` 时：采样 `isButtonPressed(0)` → `gesture.update()` → 执行动作 → `view.onAction()` → **`return true`**（吞掉原生处理）。其他索引 `return false` |
| `setup()` | 校验 `buttons[0].type` 是 `BTN_TYPE_PUSH`(2) / `BTN_TYPE_PUSH_ACT_HIGH`(3)；不匹配则禁用 HMI 并打日志（开关型/PIR 不适用本状态机） |
| `addToConfig()` / `readFromConfig()` | 新增 §6.6 的配置项 |
| `appendConfigData()` | 加 `addInfo()` 说明"启用后 button 0 的三个 macro 不再生效" |

> ⚠️ `handleIO()`（`wled.cpp:112`）在 `strip.service()`（`wled.cpp:153`）**之前**执行。**按键回调里只更新状态，不做 SPI 绘制**——否则会把一帧时间从 23 ms 拉到 35 ms，可能丢帧并影响 LED 刷新。绘制统一在 `loop()` 里做。

### 6.4 逃生通道必须复刻

HMI 接管 button 0 后，`button.cpp:331-336` 的原生 AP / 恢复出厂分支**不会再执行**。必须在 `HmiGesture::update()` 里等价实现：

```c
// 松手时按总时长分流
if (dur >= 10000)      action = ESCAPE_RESET;  // WLED_FS.format(); doReboot = true;
else if (dur >= 5000)  action = ESCAPE_AP;     // WLED::instance().initAP(true);
else if (dur >= 600)   action = ENTER/LONG;    // 亮度调节
else                   action = SHORT;         // 开关灯 / 等待双击
```

三个阈值（600 / 5000 / 10000 ms）与消抖 50 ms **直接引用 `button.cpp` 的同名常量或定义等价常量，不要各写各的魔数**，否则将来上游调整时两边会漂移。

另外两条必须明确的语义（都与 WLED 原生一致，`button.cpp:318-347`）：

- **双击在第二次"松手"时触发**，且第二次按压需 ≥50 ms 消抖——不是在第二次按下时触发。手感上是"点两下就切了"，实现上要多一轮状态。
- **双击的第二次按压若被按住不放，算长按（调亮度），不触发双击**——即"双击"的判定以"第二次按压是否是一次短按"为准。

### 6.5 绘制策略与性能预算

| 场景 | 绘制量 | 耗时估算 | 频率 |
|---|---|---|---|
| 时钟/日期走字 | 顶栏整条（160×11） | ≈ 1 ms | 1 次/分钟 |
| 亮度值/图标变化 | 顶栏整条 + 覆盖层进度条 | ≈ 1～2 ms | 按键期间每 150~200 ms |
| 电流刷新 | 底栏整条（160×11） | ≈ 1 ms | 1 次/秒 |
| 切换预设 | 主区预设名（大字）+ 标题行 | ≈ 1 ms | 每次双击 |
| 进出覆盖层 | 主区（60px 高） | ≈ 5 ms | 每次动作 |
| 开机首绘 | 全屏 | ≈ 10 ms | 1 次 |

原则：

1. **绝不 `fillScreen()` + 全量重绘**，除非确实换屏；两条状态栏都是常驻的，任何操作都不应该重绘它们（除了它们自己变的那个槽）。
2. 所有绘制走 TFT_eSPI 的批量接口（`fillRect` / `pushImage` / `drawString`），不要逐像素 `drawPixel`。
3. 绘制前后不调用 `delay()`；必要让出时用 `yield()`。
4. 检测到 `strip.isUpdating()` 为真时**可以推迟一帧再画**，避免与 LED 刷新抢 SPI/CPU（沿用 `button.cpp:268` 的思路）。

### 6.6 与 WLED 状态的交互

动作的实际写法（与 `button.cpp` 原生动作保持一致，见 `:27` / `:81`，这样 WebSocket / MQTT / UDP 同步 / `currentPreset` 归零等副作用都会自然发生）：

| 动作 | 写法 |
|---|---|
| 开关灯 | `toggleOnOff(); stateUpdated(CALL_MODE_BUTTON)` |
| 调亮度 | `bri = constrain(bri ± step, 1, 255); stateUpdated(CALL_MODE_BUTTON)` |
| 切换预设 | `applyPreset(next, CALL_MODE_BUTTON_PRESET)`——**只写请求，不写状态**。`applyPreset()` 是非阻塞的（`presets.cpp:127`），真正的应用与 `currentPreset` 的赋值都在 `handlePresets()` 里做；在按键回调里再补一句 `stateChanged = true` 只会让 `currentPreset` 被 `led.cpp:93` 清掉 |
| 切换模式（无预设时的退化） | `effectCurrent = (effectCurrent + 1) % strip.getModeCount(); stateChanged = true; colorUpdated(CALL_MODE_BUTTON)` |

按键回调里**只写变量，不做文件 IO、不取 JSON 缓冲锁**：`applyPreset()` 满足这条，而读取预设名（`getPresetName()` 会取锁并读文件）与重建预设索引都推到 `loop()` 里做。

| 情况 | 处理 |
|---|---|
| `realtimeMode` 激活（E1.31/Art-Net/DDP…） | 效果/亮度会被实时数据持续覆盖。状态栏主区显示 `LIVE` 标记（`HMI_C_WARN` 色），按键仍可操作（与原生按钮一致） |
| 改动是否持久 | **只有长按调亮度持久**。WLED 的状态易失，预设是唯一的落盘点，所以长按把**当前整份状态**写回**屏幕上显示的那个预设**（usermod 自己的 `presetCursor`，不是 `currentPreset`——见 §3.4 第 1 条），切回该预设即带回新亮度。短按开关机（会丢弃在途写回）、双击切预设都不写回；不在任何预设里时不写；播单预设跳过（写进去等于把播单抹了）。写回的内容永远是"开"的状态：`bri == 0` 时不写，免得预设因为一次随手关灯而变黑。**开机仍走 WLED 的启动亮度**，除非在 LED preferences 里指定 *Apply preset N at boot* —— 文档里要写明这一条，避免"我调好了怎么重启就没了"的误解 |
| 亮度过渡 | 直接赋值 → 无过渡，与 `button.cpp` 原生行为一致 |
| OTA / `strip.suspend()` 期间 | HMI 只更新显示，不碰 LED 状态 |
| 多段（Segment） | V1 只操作 `strip.getMainSegment()`，与现有屏幕显示的信息一致 |

### 6.7 配置项（usermod 设置页）

| 键 | 默认 | 说明 |
|---|---|---|
| `hmi` | `true` | 是否接管 button 0。关闭后按钮完全回到 WLED 原生逻辑 |
| `hmiSave` | `true` | 是否把长按调出来的亮度写回当前预设。关闭后按钮不再写任何预设 |
| `hmiDouble` | `350` | 双击窗口（ms）。**设为 0 时关闭双击手势**，短按零延迟生效 |
| `hmiStep` | `16` | 亮度加速后的步进（前 5 步固定用 4） |
| `hmiRepeat` | `150` | 按住重复间隔（ms） |
| `hmiOverlay` | `1500` | 操作态覆盖层回落时间（ms）。**这个值同时决定了亮度写回的时刻**——写回就发生在覆盖层落下、主界面回来的那一下 |

> 上表的键名是 `cfg.json` 里 `um.ST7735` 下的真实键名，也就是设置页上显示的名字（它们与源码里的成员名不完全同名：`hmiDouble` ↔ `hmiDoubleMs`，`hmiOverlay` ↔ `hmiOverlayMs`）。

> 设置页需提示：**启用 `hmi` 后，button 0 在 Time settings 页配置的三个 macro（press / long / double）不再生效**。

## 7. 关键风险与坑

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | **逃生通道失效** | 设备无法恢复，需飞线刷机 | §6.4 完整复刻 5 s/10 s；硬件下载模式兜底 |
| 2 | **GPIO9 是 strapping 引脚** | 开机按住按键 → 进下载模式，表现为"设备不启动" | 文档明确；不设计任何"开机手势" |
| 3 | 短按被双击窗口拖慢 350 ms | "按了没反应"的错觉 | 可配置（§3.2）；`hmiDoubleMs=0` 时零延迟 |
| 4 | 调亮度时不知道方向 | 按了反而变暗，体验差 | 方向指示必须在 600 ms 内出现在覆盖层（§4.3） |
| 5 | 绘制挤占 LED 帧时间 | 调亮度时灯闪 | 局部重绘 + 按键回调不绘制 + 与 `strip.isUpdating()` 错峰 |
| 6 | 状态栏在 NTP 未同步 / AP 模式下显示垃圾 | 满屏 `0:00` 或空 IP | §4.1 的降级行为表，必须逐条实现 |
| 7 | 按键接管后原生 macro 失效 | 已有用户配置失效 | 设置页提示 + `hmi` 开关可关闭 |
| 8 | 无背光控制引脚 | 无法息屏，长时间常亮（彩屏背光是持续的几十 mA） | 需求上接受；否则换带 BL 的模块（§10） |
| 9 | 现有 1 秒轮询门槛挡住立即重绘 | 按键后延迟最多 1 秒才更新 | §6.3 接线点必须一起改 |
| 10 | 按钮类型被配成开关/PIR | 状态机行为错乱 | `setup()` 校验类型，不匹配则禁用 HMI |
| 11 | 只能单向前进切预设 | 想回上一个预设要转一圈 | 接受：预设集本来就小；见 §3.4 与 §9 |
| 12 | **11×11 的图标画不成形** | 太阳读成十字、信号格糊成一团，界面显得业余 | 太阳的十字有两个来源：半径 1 的 `fillCircle` 本身退化成加号（必须用半径 2），以及**只画四根轴向光线**——这个真的发生过，见 §4.1。八根光线始终一起出现，就不会有十字；信号格同理：2px 宽、1px 间隙是这条屏上还能分辨的下限 |
| 13 | **`getPresetName()` 拿不到锁时和"预设没名字"返回同一个 `false`**（`presets.cpp:87`） | 名字取不到，或陷入每秒重试一次文件读 | 重试次数封顶（`HMI_PRESET_NAME_TRIES`），失败就退化为显示效果名，见 §3.4 |
| 14 | **索引重建条件不会被重建本身消除** | 若 `currentPreset` 指向扫描器看不到的 ID，会变成每秒重读一次文件 | 该条件按 ID 记忆（`presetCheckedId`），同一个 ID 只强制重建一次 |
